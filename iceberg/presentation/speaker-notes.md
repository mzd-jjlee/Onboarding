## 01. 레이크하우스란 무엇인가  ⏱ 3분 (~4:30)

### 3. 데이터 레이크하우스의 정의
*레이크의 저장 방식에 웨어하우스의 관리 기능을 얹은 구조*

**레이크에서 가져온 것 — 저장 방식**
- S3 · MinIO 같은 **저렴한 오브젝트 스토리지**에 파일 그대로 (전용 시스템에 안 넣으니 용량 확장이 쉬움)
- Parquet 같은 **공개 포맷** → 여러 도구가 같은 파일을 동시에 읽음, 벤더 종속 없음

**웨어하우스에서 가져온 것 — 관리 기능**
- 스키마 정의 · **변경 이력 관리(Time Travel)**
- 트랜잭션 — 쓰는 중에 조회하면 이전 상태가 보임 (쓰다 만 파일이 안 보임)
- 가져온 이유: 레이크는 파일이 제멋대로 쌓여 **데이터 늪(Data Swamp)** 이 되기 쉬움

**한 줄 정리**
> 파일은 레이크처럼 그 자리에 두고, 그 위에 **테이블을 관리하는 계층**을 얹은 것

**반드시 짚을 것**
- 칩(S3·MinIO / Snowflake·BigQuery)은 **대표 예시일 뿐, 우리가 쓴 게 아님**
- 초록 배너 — **"레이크에도 카탈로그는 있었다."** 달라진 건 **테이블 정의가 파일 쪽으로 내려왔다**는 것
- 완성 제품이 아니라서 **적재 · 테이블 포맷 · 카탈로그 · 조회를 직접 조합**해야 함 → 다음 장

> **질문 대비**
> - **"레이크엔 메타데이터 관리가 아예 없었나요?"** — 있었습니다. 지금 쓰는 Hive Metastore가 바로 그겁니다. 다만 파일 목록을 **디렉터리 스캔**으로 알아냈고, **커밋이 원자적이지 않았고**, 테이블 등록이 강제되지 않아 등록 안 된 버킷이 쌓였습니다 — 그게 '늪'의 정체입니다. (12쪽에서 HMS 다시)
> - **"Snowflake도 S3에 두지 않나요?"** — 맞습니다. 물리적으로는 오브젝트 스토리지에 파일로 둡니다. 다만 **네이티브 테이블은 포맷이 비공개라 그 엔진으로만 읽힙니다.** 차이는 *어디에 두느냐*가 아니라 *누구만 읽을 수 있느냐*입니다. (요즘은 Snowflake도 Iceberg 테이블을 지원해서 이 경계가 흐려지고 있습니다)

### 4. 레이크하우스를 이루는 네 가지 역할 ★
*완제품을 사는 대신 네 역할을 직접 조합했다*

**이 장의 첫 마디 (그대로 말해도 됨)**
> 레이크하우스는 하나의 제품 이름이 아니라 **아키텍처 패턴**입니다. Databricks나 Snowflake처럼 완제품으로 파는 플랫폼도 있고, 오픈소스를 조합해서 직접 만들 수도 있습니다. 이번 과제는 후자라서, **적재 · 테이블 포맷 · 카탈로그 · 조회 네 역할을 각각 골라 조합**했습니다.

**네 칸을 짚으며**

| 역할 | 내가 쓴 것 | 하는 일 |
|---|---|---|
| ① 적재 | **SeaTunnel** 2.3.13 | 원본 DB의 행을 읽어 레이크에 쓴다 — 파일 작성 + 테이블 커밋 |
| ② 테이블 포맷 | **Iceberg** 1.6.1 | 쌓인 파일 중 **어떤 게 현재 테이블인지** 정의, 스키마·이력도 여기 |
| ③ 카탈로그 | **Hive Metastore** 4.0.1 | 테이블 이름 → **현재 메타데이터 파일 위치**, 조회의 시작점 |
| ④ 조회 | **Trino** 483 + **Superset** 6.0 | SQL 실행 엔진 + 사람이 보는 화면 — 둘은 다른 역할 |

**반드시 짚을 것**
- 괄호 안 도구는 **저희가 고른 것일 뿐, 네 칸 모두 교체 가능**
- 아래 흐름 띠 — **쓰기는 02장, 읽기는 05장**에서 펼쳐짐

> **질문 대비**
> - **"Iceberg 칸만 왜 로고가 아니라 문서 아이콘인가요?"** — Iceberg는 **서버가 아니라 파일 포맷**이라서입니다. 6쪽 그림에도 Iceberg 상자가 없고, 11쪽에서 다시 말씀드립니다.
> - **"완제품이 있는데 왜 조립했나요?"** — **학습이 목적**이었습니다. 각 역할의 경계를 직접 보려면 조립하는 쪽이 낫습니다. 실무라면 운영 부담과 비용을 놓고 저울질할 문제고요.
> - **"Databricks·Snowflake와는 뭐가 다른가요?"** — Databricks는 Delta Lake + Unity Catalog + Spark/Photon, Snowflake는 Iceberg 테이블 + Polaris 카탈로그로 같은 역할을 묶어서 팝니다. **역할 구성은 같고, 그 경계가 제품 안에 숨어 있을 뿐**입니다. (조사한 내용이고 써본 건 아닙니다)

### 6. 로컬 배포 아키텍처 ★
*네 가지 역할을 무엇으로 띄우고 무엇으로 연결했는가*
- 전체 구성을 먼저 보여드리고 들어가겠습니다. 지금은 자세히 보실 필요 없습니다.
- 범례의 **주황이 적재, 파랑이 조회**인데 이게 오늘 설명 순서이기도 합니다.
- 손으로 짚어드릴 건 셋입니다 — **웹 브라우저만 Docker 밖**에 있고, **`lake/`는 bind mount**라 호스트와 컨테이너가 같은 파일을 봅니다. 그리고 4장에서 쓸 **1억 행 원본은 이 그림의 Source DB가 아니라 별도 PostgreSQL**입니다.

> **질문 대비** — Trino의 `lake` 마운트는 읽기 전용(`:ro`)입니다. catalog-db↔HMS 화살표는 주황으로 그려졌지만 조회할 때도 씁니다.

### 7. 적재 흐름
*파일을 쓰는 것과 테이블이 되는 것은 다른 단계*
- 실제 적재가 어떤 순서로 일어나는지 번호를 따라가 보겠습니다.
- **① `compose.yaml`** — 원천 PostgreSQL, Hive Metastore, 그 기록을 담을 catalog-db를 **Docker 컨테이너로 띄웁니다.** 서로 서비스 이름으로 통신하도록 네트워크도 여기서 잡힙니다.
- **② `catalog-tools`** — HMS에 **`retail`이라는 namespace 하나만** 만들어 둡니다. 테이블이나 데이터는 만들지 않습니다. *"테이블을 담을 이름 공간과 기본 저장 위치를 미리 등록해 두는 일회성 준비 작업"* 정도로 보시면 됩니다.
- **③ `jobs/*.conf`** — 어디서 읽고(JDBC source) 어디에 쓸지(Iceberg sink)를 설정 파일 하나에 선언합니다. 다음 두 장에서 이 파일을 열어봅니다.
- **④ 파일 작성** — SeaTunnel의 **Zeta 엔진**으로 잡이 실행되고, Iceberg sink이기 때문에 지정한 테이블 경로 아래에 **실제 행인 `data/*.parquet`과, 그 데이터를 설명하는 `metadata/*.json` · `*.avro`가 함께** 쌓입니다.
- **⑤ HMS 커밋** — 마지막으로 Hive Metastore에 커밋합니다. 여기서 넘어가는 건 **"지금 이 테이블의 현재 metadata JSON은 여기다"라는 위치 한 줄**입니다. 실제 행 데이터는 HMS로 가지 않습니다.
- 이 장의 핵심은 — **④와 ⑤가 별개 단계**라는 점입니다. 파일을 다 써도 **커밋이 되기 전까지는 아무도 그 테이블을 볼 수 없습니다.** 하단 띠에 적힌 대로 **파일 작성 후 카탈로그 커밋이 성공해야 새 상태가 공개됩니다.**

> **질문 대비**
> - "`catalog-tools`가 테이블도 만드나요?" — 아니요. namespace만 만들고 **테이블은 SeaTunnel이 적재하면서 생성**합니다. 8장의 `schema_save_mode`가 그 설정입니다.
> - 1억 행 적재 때는 PyIceberg 0.10이 Hive 4와 호환되지 않아, **SeaTunnel에 포함된 Java Iceberg/HMS 클라이언트**로 namespace를 준비했습니다 (`PrepareProductionCatalog.java`).
> - 그림의 경로가 `retail.db/orders/`인데 이건 첫 실습 테이블입니다. 1억 행 테이블은 `production_orders_100m_append/`이고 구조는 같습니다.
> - 하단 오른쪽 "APPEND 재실행 시 중복 가능" — 같은 잡을 두 번 돌리면 행이 중복됩니다. 래퍼 스크립트가 막습니다.

### 8. 적재 작업 설정
*SeaTunnel DB → Iceberg config*
- 설정 파일 하나에 **어디서 읽을지(source)와 어디에 쓸지(sink)**가 같이 선언됩니다.
- sink 쪽에 **카탈로그 주소와 저장소 경로가 함께** 들어간다는 것만 봐주시면 됩니다.
- 실제 파일에는 transform 블록도 있는데 오늘 범위 밖이라 뺐습니다.

> **질문 대비** — `APPEND_DATA`라 그냥 재실행하면 데이터가 중복됩니다. 그래서 래퍼 스크립트가 재실행을 막습니다.

### 9. Iceberg sink 설정
*주소를 두 개 알려줘야 합니다*
- 이 장의 핵심은 **주소가 두 개**라는 겁니다.
- `uri`는 **카탈로그 주소**입니다. 테이블 등록과 커밋 요청을 여기로 보냅니다.
- `warehouse`는 **저장소 주소**입니다. Parquet이나 메타데이터 파일이 실제로 여기에 쓰입니다.
- 3장에서 말씀드릴 **카탈로그와 저장소의 역할 분리가 설정 파일에 그대로 드러나** 있습니다.

> **질문 대비**
> - `warehouse`는 기본 위치일 뿐이고, 실제 위치는 카탈로그에 기록된 값이 이깁니다. 저희 테이블도 이름은 `…100m`인데 디렉터리는 `…100m_append`입니다. 그래서 `warehouse`만 바꿔서 기존 테이블을 옮길 수는 없습니다.
> - `schema_save_mode`의 '스키마'는 Postgres의 `public` 같은 네임스페이스가 아니라 **컬럼 이름과 타입**을 말합니다. 정확히는 원천 테이블 전체가 아니라 SELECT 결과 기준이고요. `CREATE TABLE`을 한 번도 쓰지 않았는데 테이블이 생긴 이유가 이 설정입니다.
> - 이 job을 두 번 돌리면 1억 행이 2억 행이 됩니다. Parquet만 실제 중복이고, JSON·Avro가 늘어나는 건 버전 이력이라 성격이 다릅니다.

### 11. 구성요소별 책임 범위 ★
- 왼쪽보다 **오른쪽 '하지 않는 일' 열을 천천히** 봐주시면 좋겠습니다.
- 특히 Iceberg 행인데요 — **Iceberg는 독립 실행 프로세스가 아닙니다.** `docker ps`를 쳐도 안 나옵니다. 파일과 그걸 읽고 쓰는 라이브러리로만 존재합니다.
- 이 표가 실제로 쓸모 있는 이유는, **문제가 생겼을 때 어디를 볼지가 정해진다**는 겁니다. 조회가 느리면 HMS가 아니라 Trino와 Parquet을 보고, 테이블이 안 보이면 파일이 아니라 카탈로그 커밋을 봅니다.

### 12. Hive Metastore의 역할
*Iceberg 테이블의 이름과 현재 metadata 위치를 기록하는 카탈로그*

**이 장의 첫 마디**
> 앞 장 표에서 한 줄이었던 **카탈로그**를 조금 더 보겠습니다. HMS가 아는 건 결국 **"테이블 이름 → 현재 metadata JSON 위치"** 하나입니다. 그 역할을 세 가지로 나눠서 보겠습니다.

**세 가지 역할 (그림 순서대로)**

| | 역할 | 하는 일 |
|---|---|---|
| ① | **이름 관리** | namespace와 테이블 이름을 등록 |
| ② | **등록 정보 조회** | 요청이 오면 **HMS가 catalog-db에서 읽어 돌려줌** — 묻는 쪽(Trino·SeaTunnel)은 DB에 직접 붙지 않음 |
| ③ | **등록 정보 갱신** | writer 요청에 따라 `metadata_location`을 새 JSON 위치로 변경 — **이게 "커밋"의 실체** |

**반드시 짚을 것**
- 그림 아래 *"커밋은 writer의 Iceberg 구현과 협력"* — **커밋을 HMS 혼자 하는 게 아니라, writer가 요청하고 HMS가 위치를 바꿔주는 구조**라는 뜻. 한 줄만 짚고 넘어간다
- 그림의 `retail namespace · orders 테이블`은 **내가 지은 이름** → 말할 땐 *"namespace와 테이블 이름을 등록합니다"* 로 일반화
- **HMS는 우리가 개발한 게 아니라 공식 Hive 이미지를 설정해 실행한 것** — 조립이 기본이라는 메시지와 연결
- 하단 띠 — **Parquet 작성 · manifest 생성 · SQL 집계는 HMS가 안 함.** 파일 작성은 Iceberg writer, 읽기와 계산은 Trino
- 한 줄 정리: **역할이 이렇게 작게 잘려 있어서 카탈로그를 바꿔도 파일은 그대로**

> **질문 대비**
> - **"writer가 둘이 동시에 커밋하면 어떻게 되나요?"** — HMS가 **위치 교체를 원자적으로 보장해 한쪽만 성공**한다고 문서에 나와 있습니다. 다만 **저희는 단일 writer만 돌려서 확인하지 못했습니다.** → 여기서 멈춘다. 더 들어가지 않는다
> - **"HMS가 꼭 필요한가요?"** — 모든 Iceberg 구성의 필수는 아닙니다. **JDBC · REST · Glue** 같은 카탈로그 대안이 있습니다. (조사한 내용이고 써본 건 아닙니다)
> - **"HMS에 데이터도 들어가나요?"** — 아니요. 행과 스키마·파일 목록·통계는 전부 `./lake`의 Parquet·JSON·Avro에 있고, **HMS에는 그 JSON의 위치 한 줄**만 갑니다. 다음 장에서 직접 열어봅니다.

### 13. 카탈로그에 실제로 저장된 값
*catalog-db(PostgreSQL) 직접 조회 결과*

**이 장의 첫 마디 (그대로 말해도 됨)**
> HMS가 메타데이터를 처리하려면 **내부 저장소가 하나 있어야 해서, PostgreSQL을 띄워 붙였습니다.** 열어보면 이런 값들이 들어 있습니다 — **metadata JSON의 위치, 현재 snapshot id, 테이블 스키마, 행 수**까지요.

**화면에서 짚을 것 (카드 ①②③ 순서대로)**
- ① **`metadata_location`** — 현재 테이블을 가리키는 줄. **커밋은 이 값을 바꾸는 일**이고, 바로 아래 `previous_metadata_location`에 직전 값이 남아 **교체 흔적**이 그대로 보인다
- ② **`numRows` · `numFiles` · `totalSize` · `snapshot-count`** — **HMS가 센 값이 아니라 적재한 쪽이 계산해 넘긴 값**을 보관만 한다. HMS는 스냅샷이 뭔지도 모른다
- ③ **쓰이는 테이블은 넷뿐** — metastore의 70여 개 중 `TBLS` · `TABLE_PARAMS` · `SDS` · `COLUMNS_V2`
- 1억 행짜리 테이블인데 **HMS 기록은 전부 합쳐 수십 행**이다. 카탈로그가 하는 일이 그만큼 작게 잘려 있다

**마무리 (그대로 말해도 됨 — 04장으로 넘어가는 다리)**
> HMS가 꼭 쥐고 있어야 하는 건 사실상 **`metadata_location` 한 줄**이고, 나머지는 참고용입니다. **진짜 정보는 전부 파일 쪽에 있고, 그걸 4장에서 하나씩 따라가 보겠습니다.**

> **질문 대비**
> - **"그럼 이 DB만 열면 되는 거 아닌가요?"** — 안 됩니다. 셋이 빠져 있습니다.
>   **(1) 파일 목록이 없습니다.** `numFiles`가 4라고 개수는 있는데 **어느 파일인지가 없어서**, 이 DB만 보고는 읽을 파일을 하나도 못 찾습니다. 경로와 컬럼 통계는 manifest에만 있습니다.
>   **(2) "현재" 것만 있습니다.** 스냅샷이 4개인데 id는 하나뿐이라 **과거 시점 조회가 안 됩니다.** `current-schema`도 하나뿐이고요.
>   **(3) 권위가 없는 요약 사본입니다.** HMS엔 `numRows`가 1억 하나뿐인데, 시점 조회를 하면 2,500만·5,000만·7,500만이 나옵니다 — **Trino가 이 값을 안 쓰고 파일을 따라가 센다는 뜻**입니다. `DO_NOT_UPDATE_STATS: true`가 붙어 있는 것도 같은 표시입니다.
> - **"왜 그렇게 설계했나요?"** — Iceberg 스펙상 카탈로그가 **반드시 보장해야 하는 건 "테이블 이름 → 현재 metadata 위치" 하나**입니다. 진실이 DB에 있으면 **카탈로그를 바꾸는 순간 테이블을 잃습니다.** 14쪽에서 "카탈로그는 교체 가능"이라고 말할 수 있는 근거가 이겁니다.
> - 접속은 `localhost:15432 / hive / hive / metastore`입니다. 등록된 테이블은 `orders`, `production_orders_100m`, 그리고 실패 시도 잔재인 `production_orders_100m_attempt1` 셋입니다. `PARTITIONS` · `TAB_COL_STATS` · `HIVE_LOCKS`는 0행입니다.

### 16. Iceberg가 만드는 파일 네 가지
*메타데이터에서 실제 행까지 한 단계씩 따라간다*
- 왼쪽이 Iceberg가 만드는 **파일 네 종류**고, 오른쪽은 **실제 테이블 폴더에 쌓인 파일 17개**입니다. 번호 색과 파일 색을 맞춰 뒀습니다.
- **용어 두 개를 여기서 먼저 풀고 간다** (카드의 회색 작은 줄). 처음 듣는 사람에게는 이 두 단어가 벽이다 — 그냥 읽어주면 된다
  - **스냅샷** = *"커밋 한 번이 만든 그 시점의 테이블 전체 모습"* → 17쪽에서 JSON 안의 배열로 직접 보여준다
  - **manifest** = *"데이터 파일의 목록"*, **manifest list** = *"그 목록들을 모은 목록"* → 목록이 두 층이라 헷갈리기 쉬우니 **"목록의 목록"**이라고 한 번 더 말해준다
- 조회는 위에서 아래로 내려옵니다. ① JSON 한 개에서 시작해서 ② manifest list, ③ manifest를 거쳐 ④ Parquet에 닿아야 비로소 실제 행을 읽습니다. **앞의 셋은 전부 "어디를 열지"를 정하는 단계**입니다.
- 오른쪽에서 **확장자를 봐주세요.** JSON은 맨 위뿐이고 **가운데 둘은 Avro**입니다.
- 자료를 찾다 보면 "manifest는 JSON"이라는 설명이 종종 보이는데, 실제 파일은 그렇지 않습니다.
- 다음 네 장에서 ① → ② → ③ → ④ 순으로 하나씩 열어보겠습니다.

> **질문 대비**
> - metadata JSON이 **5개**인 이유는 빈 테이블 생성 1회 + 커밋 4회입니다. 조회가 쓰는 건 카탈로그가 가리키는 `00004` 하나뿐이고, 나머지는 이력입니다.
> - `snap-*.avro`가 4개인 건 **스냅샷당 1개**, `-m0.avro`가 4개인 건 **커밋당 1개**라서입니다.
> - Parquet 4개는 적재 병렬도가 4였기 때문이고, 합쳐서 330.5 MB입니다.

### 17. ① metadata JSON — 현재 스냅샷 선택
*테이블의 현재 상태가 적힌 파일*
- 실제 JSON입니다. 보기 좋게 주요 필드만 추렸고, 값은 실제 파일 그대로입니다.
- **커밋이 일어날 때마다 스냅샷 항목이 배열에 하나씩 덧붙습니다.** 기존 항목을 고치지 않고 추가만 합니다. 각 항목의 `total-records`는 **그 시점까지의 누적 행 수**입니다.
- 이번 실행은 병렬도 4에 커밋이 네 번이었는데, **병렬도와 커밋 수가 항상 같지는 않습니다.**
- **네 항목 모두 자기 `snapshot-id`를 가지고 있습니다.** 맨 위 `current-snapshot-id`가 `3279400440120366835`인데, 배열에서 **같은 값을 가진 항목**을 찾아서 그 항목의 `manifest-list` 경로로 넘어갑니다. 조회가 하는 일은 이게 전부입니다.
- 눈으로 따라가기 쉬운 게, **`snapshot-id`가 manifest list 파일 이름에도 그대로 들어 있습니다** — `snap-3279400440120366835-….avro`처럼요.
- 그리고 **1·2·3번 스냅샷도 지워지지 않고 그대로 남아 있습니다.** 그래서 과거 시점을 지정해서 조회할 수 있고, 각 항목의 `parent-snapshot-id`가 직전 스냅샷을 가리켜 사슬을 이룹니다.
- **되돌리기는 `current-snapshot-id`를 과거 값으로 바꾸는 일**입니다. 데이터 파일을 옮기거나 지우는 게 아닙니다.
- 한 가지만 더 — **스냅샷은 별도 파일이 아니라 이 JSON 안의 배열 원소**입니다.

> **질문 대비**
> - 새 metadata JSON이 생길 때마다 과거 스냅샷이 **함께 복사되어 들어갑니다.** 같은 ID가 여러 JSON에 반복되는 건 정상이고, 데이터를 복제한 게 아닙니다.
> - `sequence-number`는 커밋 순서, `snapshot-id`는 그 커밋의 식별자입니다. 둘은 다른 값입니다.
> - 시점 조회(`FOR VERSION AS OF`)와 롤백은 다릅니다. 앞은 읽기만, 뒤는 카탈로그가 가리키는 포인터 자체를 바꿉니다.

### 18. ② manifest list — 참조하는 manifest 목록
*고른 스냅샷이 어떤 manifest들로 이뤄졌는지*

**🧭 여기서 한 번 환기** — *"네 단계 중 두 번째입니다. JSON에서 스냅샷을 골랐고, 지금은 그 스냅샷이 어떤 manifest들로 이뤄졌는지 보는 중입니다."*
- 앞 장에서 `current-snapshot-id`로 고른 스냅샷이 가리키던 파일 — `snap-3279400440120366835-….avro` — 을 **그대로 열어본 결과**입니다. Avro라서 `fastavro`로 읽었습니다.
- 안에 **레코드가 네 개** 있고, 각 레코드의 `manifest_path`가 **`…-m0.avro`를 가리킵니다.** 즉 이 파일을 열면 **manifest 파일 네 개의 위치**가 나옵니다.
- 각 레코드의 `added_files`가 **1**입니다. **manifest 하나가 Parquet 하나를 가리킨다**는 뜻이고요. 다만 이건 **이번 실행이 그렇다는 것이지 규칙은 아닙니다** — manifest 하나가 Parquet 여러 개를 담을 수 있습니다 (다음 장).
- 네 manifest 중 **셋은 이전 커밋이 만든 것**인데, **현재 스냅샷이 그대로 다시 참조**합니다. 새 커밋이 기존 것을 덮어쓰지 않는다는 게 여기서 보입니다.
- 그리고 **2,500만 × 4 = 1억**이 나옵니다. **Parquet을 하나도 열지 않고** 레코드 수만 더해서 전체 행 수가 나온 겁니다.

> **질문 대비**
> - `seq` 순서가 뒤섞인 건 병렬로 썼기 때문이고, 목록의 순서에는 의미가 없습니다.
> - 파일 이름으로도 이어집니다 — `snap-3279400440120366835-1-7418ba24-….avro`의 뒤쪽 UUID가 첫 레코드의 manifest `7418ba24-….-m0.avro`와 같습니다.
> - 각 레코드에는 `added_snapshot_id`도 있어서, **그 manifest를 만든 커밋이 어느 스냅샷인지** 알 수 있습니다.

### 19. ③ manifest — Parquet 경로와 통계 ★
*메타데이터만으로 읽을 파일을 고른다*
- 이 장이 4장의 핵심입니다.
- 표에 보이는 값은 **전부 manifest 파일(`…-m0.avro`) 안에 적혀 있던 내용**입니다. **데이터 파일의 경로**와 함께 **행 수 · 파일 크기 · 컬럼별 최솟값/최댓값**이 같이 들어 있습니다.
- 그 경로를 따라가 보니 1억 행이 **2,500만 행씩 네 개의 Parquet으로 나뉘어** 저장돼 있었고, `order_id` 범위도 파일마다 딱 잘려 있었습니다.
- 그래서 `WHERE order_id = 7` 같은 조회라면 **범위가 겹치는 파일 하나만 후보**가 되고, 나머지 세 개 — 약 **248MB · 7,500만 행은 읽기 대상에서 빠집니다.**
- 정리하면, **대용량 테이블이라도 전체를 훑지 않고 메타데이터만 보고 필요한 파일을 골라 읽을 수 있다**는 것이 Iceberg가 주는 이점입니다.
- 다만 공짜는 아닙니다 — **통계가 효과를 내려면 값이 파일마다 뭉쳐 있어야** 합니다.

> **질문 대비**
> - 표가 manifest 1 : Parquet 1로 보이는데 **규칙은 아닙니다.** 이번 실행이 커밋마다 파일 하나씩이라 그렇게 된 것이고, manifest 하나가 Parquet 여러 개를 담을 수 있습니다.
> - 효과가 없는 컬럼의 예 — 같은 manifest에서 `status`는 네 파일 모두 `CANCELLED ~ IN_PROGRESS`, `factory_id`는 모두 `F001 ~ F030`이라 하나도 걸러내지 못합니다.
> - 후보로 남은 2,500만 행짜리 파일도 전부 읽는 건 아닙니다. Parquet 내부의 **row group과 컬럼 선택**으로 한 번 더 줄어듭니다 (다음 장).

### 20. ④ Parquet — 실제 행 데이터
*따라간 경로의 끝에 실제 데이터가 있었다*
- 체인의 마지막입니다. **manifest에 적힌 경로를 그대로 따라가서 Parquet 파일을 직접 열어봤습니다.**
- 왼쪽이 그 파일의 첫 5행입니다. 2,500만 행 중 샘플이고요. **같은 행을 Trino로 조회해도 값이 같았습니다** — 어느 경로로 읽든 같은 데이터가 나옵니다.
- 오른쪽이 이 장에서 보여드리고 싶은 부분입니다. **manifest가 적어둔 행 수와, 파일을 열어서 footer로 센 행 수를 네 파일 전부 대조**했습니다. 모두 2,500만 행으로 같았고 합계도 정확히 1억입니다.
- 앞 장에서 **"메타데이터만 보고 읽을 파일을 고른다"**고 말씀드렸는데, 그게 성립하려면 **메타데이터가 실제 파일과 어긋나지 않아야** 합니다. 이 표가 그걸 확인한 결과입니다.
- 값 자체가 **원본 DB와 같은지**는 전체 집계로 따로 대조했고, **26쪽**에서 보여드리겠습니다.

> **질문 대비**
> - Parquet은 **컬럼 단위로 저장**됩니다. `SELECT status`라면 row group 전체의 **0.09%만** 읽으면 되고, 행 단위로 저장했다면 나머지 다섯 컬럼까지 같이 읽어야 했을 겁니다. 파일당 row group은 6개입니다.
> - 읽은 방법은 **PyIceberg나 Spark가 아니라 `fastavro`와 `pyarrow`**입니다. manifest(Avro)는 fastavro로, Parquet은 pyarrow로 직접 읽었습니다.
> - 원본 PostgreSQL은 현재 기동돼 있지 않아서, 26쪽 원본 측 수치는 **적재 시점에 기록해 둔 값**입니다. Iceberg 측은 2026-10-20에 다시 재서 일치를 확인했습니다.

### 21. Iceberg 파일 관리의 이점
*앞에서 본 메타데이터 구조가 실제로 무엇을 가능하게 하는가*

**이 장의 첫 마디**
> 앞에서 파일 네 가지를 따라가 봤는데, **그 구조가 실제로 뭘 가능하게 하는지** 네 가지로 정리했습니다. 공통점이 하나 있는데, 그건 마지막에 말씀드리겠습니다.

---

**① 스냅샷 기반 시점 보존과 롤백**
- 그대로 말할 문장 — *"Iceberg는 적재 커밋 때마다 스냅샷이 남기 때문에, **이전 상태로 돌아갈 수 있고 과거 시점 조회가 용이하다**는 장점이 있습니다."*
- **예시 (실제로 해본 것)** — 작은 `retail.orders` 테이블은 배치 2회로 적재했다. 지금은 **5행 / 합계 170,000**인데, 첫 번째 스냅샷을 지정해서 조회하니 **3행 / 69,000**이 나왔다
  ```sql
  SELECT count(*), sum(amount) FROM iceberg.retail.orders
  FOR VERSION AS OF 2162422063555107563;   -- → 3행 / 69,000
  ```
- 1억 행 테이블도 같은 구조다 — 스냅샷 4개가 25,000,000 → 50,000,000 → 75,000,000 → 100,000,000 누적으로 남아 있다 (17쪽)
- **단서**: 시점 조회는 해봤지만 **되돌리기(rollback)는 안 해봤다.** Trino 카탈로그를 `READ_ONLY`로 걸어둬서 쓰기가 아예 안 된다

---

**② 메타데이터 통계 기반 파일 프루닝**
- 19쪽에서 이미 봤으니 짧게 — manifest의 컬럼별 min/max로 **파일을 열기 전에 후보를 거른다**

---

**③ 컬럼 ID 기반 스키마 진화**
- 컬럼마다 **바뀌지 않는 정수 ID**가 붙고, **그 ID가 Parquet 파일 안에도 들어 있다**
- 읽을 때 **이름이나 위치가 아니라 ID로 짝을 짓는다** — 이게 전부이자 핵심

**예시 ⓐ — 중간 컬럼을 지우면**

| | 기존 방식 (이름·위치 매칭) | Iceberg (ID 매칭) |
|---|---|---|
| `product_name`(3번)을 삭제하면 | 뒤 컬럼이 한 칸씩 **밀려서** `quantity` 자리에 날짜가 읽히는 사고 | ID 3이 스키마에서 빠질 뿐, **4·5·6은 그대로** |

**예시 ⓑ — 지운 이름을 나중에 다시 쓰면 (ID의 진가)**
- `status`(6번)를 지웠다가, 나중에 **같은 이름으로** 컬럼을 다시 추가한다
- 이름으로 매칭하면 → **옛 파일의 옛 `status` 값이 새 컬럼에 섞여 들어온다**
- Iceberg는 새 컬럼에 **ID 7**을 준다. 옛 파일엔 7번이 없으니 **NULL로 읽힌다.** 섞이지 않는다
- 이걸 보장하는 게 metadata JSON의 **`last-column-id`** 필드다 — 우리 테이블은 `6`이라 다음 컬럼은 무조건 7번이 된다. **ID를 재사용하지 않는다**

**그래서 뭐가 좋은가**
- **엔지니어** — 이름 변경 · 컬럼 추가 · 순서 변경이 **metadata JSON의 글자만 바꾼다.** 1억 행이어도 Parquet을 한 줄도 다시 쓰지 않으니 **몇 초에 끝나고, 그동안 테이블이 잠기지 않는다**
- **조회하는 사람** — 스키마를 바꿔도 **과거 값이 엉뚱한 컬럼에 섞이지 않는다.** 그리고 스냅샷마다 `schema-id`가 붙어 있어서, 과거 시점을 조회하면 **그 시점의 스키마로** 읽힌다
- **단서**: 우리가 확인한 건 **ID가 JSON과 Parquet 양쪽에 같은 값으로 들어 있다는 것까지**다. 스키마 변경 자체는 해보지 않았다 (카드의 ◐ 표시)

---

**④ 숨은 파티셔닝과 파티션 명세 진화**

**(1) 숨은 파티셔닝 — 슬라이드를 그대로 읽으면 된다**
> **나누는 규칙을 테이블에 등록**해둡니다. 예를 들어 **주문 날짜를 월별로 나눠 저장**한다고 등록해두면, 사용자는 `WHERE order_date = DATE '2026-09-14'`처럼 **원래 컬럼으로만 조회**해도 엔진이 **9월 파일만 후보로 남기고** 그 안에서 14일 행을 찾습니다. `order_month` 같은 조건을 따로 쓸 필요가 없어서 **"숨은"** 파티셔닝이라고 부릅니다.

- 기존 Hive 방식: 월별 파티션을 하려면 `order_month` 같은 **파생 컬럼을 테이블에 직접 만들어** 넣고, 조회할 때도 사용자가 그 컬럼을 명시해야 파티션 프루닝이 걸렸다. `order_date` 조건만 쓰면 **그 파티션 프루닝은 못 탄다** (파일 통계 같은 다른 최적화까지 없어지는 건 아니다 — "무조건 풀스캔"이라고 말하지 말 것)
- Iceberg: 명세에 **`month(order_date)`라는 변환 규칙만 등록**한다. 테이블 컬럼은 그대로고 파생 컬럼이 생기지 않는다
- **파티션이 조건을 완전히 대체하진 않는다** — 9월 파일 안에는 9월 1~13일도 들어 있으므로, **파티션으로 후보를 줄인 뒤 원래 날짜 조건을 다시 평가**한다. 정확히는 *"안전하게 제외할 수 있는 파티션을 계산하고, 남은 후보에 필터를 적용한다"*

**(2) 명세 진화 — 과거를 안 건드리고 기준을 바꾼다**
> 나중에 **규칙을 월별에서 일별로 바꿔도** 기존 파일은 월별 그대로 두고, 새로 쓰는 파일만 일별로 쌓입니다. **조회 SQL은 그대로**입니다 — 엔진이 파일마다 어느 규칙으로 쓰였는지를 보고 알아서 고릅니다.

- metadata JSON의 **`partition-specs`가 배열**인 게 그 자리다. 기존 spec은 남고 새 spec이 추가된다
- 각 파일이 어느 명세로 쓰였는지는 **manifest에 적혀 있다** — manifest 스키마에 `partition` 슬롯이 있고 `"schema based on the partition spec"`이라고 주석이 달려 있다. **우리 파일은 이 슬롯이 `{}`로 비어 있다** (명세가 `fields: []`라서)
- **기존 파일이 자동으로 일별 재분할되지는 않는다.** 과거 데이터까지 새 기준으로 재배치하려면 **별도 재작성 작업**이 필요하다

**"그냥 DB는 안 되나?" 라고 물으면**
- 파생 컬럼 쪽은 — PostgreSQL도 표현식으로 파티션 키를 잡을 수 있어서 **Iceberg만의 것은 아니다.** 다만 Hive 테이블에서는 파생 컬럼이 사실상 필수였고, **조회할 때도 그 컬럼을 명시해야 했다**는 게 차이다
- 진짜 차이는 **기준 변경**이다. **PostgreSQL은 이미 만든 파티션 테이블의 파티션 키를 바꿀 수 없다.** 새 테이블을 만들고 `INSERT ... SELECT`로 전부 옮겨야 한다 — **전면 재작성**이다
- (이 비교는 조사·일반 지식이고, 이번 과제에서 돌려본 것은 아니다)
- **단서**: 카드의 `◌ 설명용 예시` 표시를 짚는다. **이번 테이블은 비파티션(`fields: []`)이라 ④는 써보지 못했다**

**질문 대비 — ④에서 나올 만한 것**
- **"왜 파티션을 안 썼나요?"** → **실습 범위에서 뺀 선택이지 성능상 불필요하다고 입증한 건 아니다.** 1억 행이 Parquet 4개라 단일 노드에서는 쪼갤 이유가 적었고, 이번 조회가 주로 전체 집계와 `order_id` 범위라서 min/max 통계로 충분했다. **파티션 필요성은 행 수가 아니라 "주로 어떤 조건으로 조회하는가"를 보고 판단해야 한다**고 답한다
- **"②번 통계 프루닝이랑 뭐가 다른가요?"** → ②는 **파일에 실제로 들어간 값의 범위**로 거르고, ④는 **쓸 때 의도적으로 값끼리 모아둔 것**이다. 다만 ②도 정렬·배치 설계로 효과를 **의도적으로 높일 수 있고**, 둘은 **같이 쓴다.** "④가 항상 더 강하다"고 말하지 말 것
- **"변환이면 아무 함수나 되나요?"** → 아니다. `year`·`month`·`day`·`hour`·`truncate`처럼 **원래 조건에서 제외할 파티션을 추론할 수 있는 변환**만 쓴다. `bucket`은 순서를 보존하지 않아 **범위 조건에는 못 쓰고 `=` 조건에만** 걸린다. **"순서 보존이 전부"라고 설명하면 bucket에서 틀린다** — "변환마다 조건 추론 규칙이 정해져 있다"가 정확하다

**마무리 한 줄 (하단 띠)**
> 네 가지 모두 **데이터 파일을 다시 쓰지 않는다**는 공통점이 있습니다. 스냅샷 · 통계 · 컬럼 ID · 파티션 명세는 **전부 메타데이터 쪽에서 처리**되고, **Parquet은 한 번 쓰면 그대로**입니다.

**근거 표시를 반드시 짚을 것**
- ① ② — 앞 장에서 **실제로 확인**
- ③ — 파일에서 **ID만 확인**, 스키마 변경은 미실행
- ④ — `◌ 설명용 예시` = **미사용**

> - 로컬 파일시스템은 단일 노드 전용입니다. 다중 노드로 가면 S3 호환 저장소가 전제인데, 그건 설계만 있고 검증은 못 했습니다.

### 25. Superset SQL Lab 조회

**🔴 여기서 브라우저로 전환** — 스택이 떠 있으면 화면을 클릭해 `localhost:8088`을 새 탭으로 연다. 안 떠 있으면 스크린샷 그대로 설명하고 넘어간다.
- 실제 화면입니다. 브라우저 주소는 `localhost:8088`인데 **데이터는 `./lake`의 Parquet에 있습니다.** Superset은 사본을 갖지 않습니다.
- 왼쪽 Database가 **Trino**로 되어 있는 것 보이시죠. **Superset은 Iceberg에 직접 붙지 않습니다.**
- 테이블 이름 `iceberg.retail.production_orders_100m`에서 **`iceberg`는 Trino 카탈로그 파일명, `retail`은 HMS namespace**입니다. 앞 장 설정이 그대로 SQL 한 줄이 된 겁니다.
- 1,000행 응답에 2.3초가 나왔는데, **한 번 실행한 기록이지 성능 측정값은 아닙니다.** `limit 1000`이라 1억 행을 다 읽지도 않았고요.

> **질문 대비**
> - 연결은 어떻게 했나 — 공식 Superset 이미지에 Trino 드라이버가 없어서 Dockerfile에서 Superset의 venv에 설치했고, 스크립트가 REST API로 `trino://superset@trino:8080/iceberg`를 등록합니다. MySQL 붙일 때와 같은 절차라 본문에서는 뺐습니다.
> - 주소가 셋으로 갈립니다 — 호스트 브라우저는 `localhost:8081`, Superset 컨테이너는 `trino:8080`, Trino 자기 자신은 `localhost:8080`입니다.
> - 왼쪽 목록의 `…_attempt1`은 실패 시도 잔재이고 정리 대상입니다.

### 26. 원본과의 집계 대조 검증
*"적재됐다"와 "값이 맞다"는 다르다*
- 마지막으로, **값이 맞는지** 확인한 결과입니다.
- 이 장을 넣은 이유부터 말씀드리면 — **메타데이터가 정상인 것과 업무적으로 올바른 적재는 다릅니다.** 조회 조건을 잘못 써서 1억 행 중 9천만 행만 가져왔다고 해도 **Iceberg는 그 9천만 행을 아무 문제 없이 커밋합니다.** 스냅샷도 manifest도 통계도 전부 정상이고, 틀린 건 데이터뿐인데 그건 엔진이 알 수 없습니다. **그걸 확인하는 건 사람 몫**이라 직접 대조해봤습니다.
- 원본 PostgreSQL 집계와 Trino의 실제 파일 스캔 결과를 항목별로 대조했고 전부 일치했습니다.
- 전체 행 수만 본 게 아니라 **`order_id` 합계, NULL 개수, 문자열 길이 합계, 날짜 범위까지** 성격이 다른 지표를 두루 맞춰봤습니다.
- 이런 지표가 전부 일치했다는 건, **행이 누락되거나 값이 변형되지 않고 그대로 옮겨졌다**고 볼 수 있는 근거입니다.
- 다만 **집계 대조이지 행 단위 전수 비교는 아니라는 점**은 말씀드리겠습니다.

> **질문 대비** — 표의 모든 수치는 2026-10-20에 같은 쿼리로 다시 재서 적재 시점 기록과 완전히 일치함을 확인했습니다. 원본 PostgreSQL은 현재 기동돼 있지 않아 원본 쪽 열은 적재 시점 기록입니다. 기존 5행짜리 `orders` 테이블도 그대로 보존된 것을 함께 확인했습니다.

**다음 장으로** — 이 표를 띄워둔 채 *"마지막으로 오늘 확인한 것을 정리하겠습니다"* 하고 넘어간다.
