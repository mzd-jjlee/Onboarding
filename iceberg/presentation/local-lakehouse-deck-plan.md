# 발표 기획: 로컬 데이터 레이크하우스 환경 구축하기

작성일 2026-10-12. 산출물은 같은 폴더의 [local-lakehouse.html](local-lakehouse.html)이다.
이 문서는 **무엇을 왜 그 순서로 말할지**를 정한 기획서이고, HTML은 그 기획을 구현한 슬라이드다.

## 1. 발표 개요

| 항목 | 내용 |
|---|---|
| 주제 | 로컬 데이터 레이크하우스 환경 구축하기 |
| 대상 | 팀원 (데이터 엔지니어링 배경, Iceberg·Trino는 처음일 수 있음) |

| 형식 | 단일 HTML (브라우저에서 바로 실행, PDF 인쇄 가능) |
| 선행 발표 | `Onboarding/seatunnel/docs/slides/seatunnel-practice-share.pptx` (SeaTunnel 실습 공유) |

### 선행 발표와의 관계

SeaTunnel 발표는 **“SeaTunnel이라는 도구를 어떻게 쓰는가”** 였다.
이번 발표는 **“여러 도구를 어떻게 조립해 하나의 환경으로 만들었는가”** 다.
SeaTunnel은 이번 발표에서 네 가지 역할 중 하나(적재)로만 등장하고, 도구 자체의 개념
(Source–Transform–Sink, Zeta 엔진)은 **이미 공유한 내용**으로 넘긴다.

**이 발표가 답해야 하는 질문은 하나다 — “이 환경을 제대로 이해하고 세웠는가?”**
개별 도구의 사용법이나 디버깅 무용담이 아니다.

## 2. 핵심 메시지

> **레이크하우스는 하나의 제품이 아니라 적재 · 테이블 포맷 · 카탈로그 · 조회
> 네 가지 역할의 조합이다. 각 역할이 무엇을 하고 무엇을 하지 않는지,
> 그리고 역할들이 어디서 만나는지를 알아야 환경을 이해한 것이다.**

### 보조 메시지 3개

1. **각 구성요소는 교체 가능하다.** 그러려면 역할 경계가 분명해야 한다.
   Iceberg가 오픈 포맷이라는 사실만으로 되는 게 아니라, 카탈로그와 저장소가
   어디서 어떻게 맞물리는지가 정해져 있어야 한다.
2. **쓰기 경로와 읽기 경로는 서로를 모른다.** 두 경로는 카탈로그(HMS)와
   파일 저장소(`/lake`) **단 두 지점**에서만 만난다. 이것이 교체 가능성의 실체다.
3. **조립의 자유에는 경계를 책임지는 비용이 따른다.** 환경을 세우며 막힌 지점들은
   전부 도구 하나의 결함이 아니라 도구 사이의 접점에서 생겼다.

### 이 발표의 범위 — 두 축 (2026-10-13 확정)

**이번 과제에서 중요한 것은 아래 두 가지다.** 슬라이드 분량도 이 두 축에 몰아줬다.

| 축 | 질문 | 해당 슬라이드 | 분량 |
|---|---|---|---|
| **① 환경 세팅** | 로컬에 레이크하우스를 세우려면 **무엇이 왜 필요하고, 어떻게 붙는가** | 6~12쪽 (02·03장) | 6장 |
| **② Iceberg 동작 원리** | Iceberg가 **메타데이터로 데이터를 어떻게 효율적으로 찾아오는가** | 14~20쪽 (04장) | 7장 |

본문 22장 중 **13장(59%)이 이 두 축**이다. 나머지는 이 둘을 받치는
도입(01장)·조회(05장)·정리(06장)다.

**반대로, 이번 과제의 중심이 아닌 것:**

- **특정 적재 도구를 쓰면서 겪은 문제** — SeaTunnel의 Iceberg sink에서 어디서 메모리가
  찼는지 같은 이야기. 이건 그 도구·그 버전에만 해당하고, 레이크하우스를 이해하는 데
  보탬이 되지 않는다. 선행 SeaTunnel 발표의 영역이기도 하다.
- **적재 성능 수치** — 159초·초당 처리량 같은 값. 22·28쪽에서 결과로만 보이고
  따로 다루지 않는다. 단일 실행 기록이지 벤치마크가 아니다.

**판단 기준 한 줄:** *“이 내용이 SeaTunnel 대신 Spark를 썼어도 똑같이 유효한가?”*
아니라면 이번 발표의 중심이 아니다.

## 3. 스토리 아크

### 개정 (2026-10-15) — 목차를 다섯 섹션으로 다시 짰다

이전 구조는 **03 「오케스트레이션 ① 쓰기 경로」 / 05 「오케스트레이션 ② 읽기 경로」** 로
나뉘어 있었다. 아래 이유로 바꿨다.

1. **“오케스트레이션”이라는 말이 추상적이다.** 무엇을 보게 될지 목차만 보고 알 수 없다.
2. **쓰기/읽기로 가르니 같은 주제가 떨어졌다.** 환경 배치(6쪽)와 적재 흐름(13쪽)은
   “로컬에 이걸 어떻게 세웠나”라는 한 덩어리인데 02장과 03장으로 갈라져 있었다.
3. **청자가 궁금해하는 순서와 달랐다.** “뭔데? → 어떻게 세웠는데? → 각자 무슨 일 하는데?
   → 파일은 어떻게 관리되는데? → 그래서 어떻게 보는데?” 가 자연스럽다.

### 새 구조

```
[01] 데이터 레이크하우스 정의        웨어하우스·레이크와 무엇이 다른가 → 네 가지 역할
      ↓
[02] 로컬 레이크하우스 아키텍처       Mac 한 대에 어떻게 세웠나 — 원본 DB → SeaTunnel
     (저장까지. Trino·Superset 제외)   → Iceberg 파일 + HMS 커밋까지
      ↓
[03] 구성요소의 역할과 경계          각자 하는 일 / 하지 않는 일 · 카탈로그의 자리
      ↓
[04] Iceberg가 파일을 관리하는 방법   ★ 저장된 JSON·Avro·Parquet를 한 장씩 열어본다
                                   + Iceberg가 표준처럼 쓰이는 이유
      ↓
[05] Trino·Superset으로 조회하기     조회 계층을 붙이고 실제로 읽는다
      ↓
[06] 정리                          전체 지도 → 확인한 것 → 남은 것
```

**02와 05가 Trino·Superset을 기준으로 갈린다.** 02는 **저장까지**만 세우고,
05에서 **조회 계층을 얹는다.** 실제 구축 순서(`up.sh` → `up-trino.sh` → `up-superset.sh`)와
같은 순서라 설명하기 쉽고, 02장 그림(`09-basic-container-environment`)에 Trino·Superset이
없는 것과도 맞는다.

의도했던 내용은 이것이었다 — *SeaTunnel(쓰기)과 Trino(읽기)는 서로의 존재를 모르고,

**안 읽힌 이유는 은유가 틀려서다.** 두 경로는 시간상 만나지도 않는다 —
SeaTunnel은 적재할 때만 실행되고 조회 시에는 뜨지도 않는다. “만난다”가 아니라
**“같은 두 가지를 쓸 뿐”** 이 정확하다.

**대신 04장 「왜 Iceberg가 표준처럼 쓰이나」의 “엔진 독립” 항목으로 접어 넣는다.**
같은 메시지가 이미 4쪽(각 칸은 교체 가능)과 30쪽(확인한 것)에 있어 독립 장이 필요 없고,
한 항목으로 쓰면 질문 형태로 구체화된다 —
*“SeaTunnel을 Spark로 바꾸면 Trino 설정을 고쳐야 하나? → 아니다.
공유하는 건 HMS 주소와 `/lake` 경로 두 줄뿐이다.”*

### 04장에 새로 만들 슬라이드 — “왜 Iceberg가 표준처럼 쓰이나”

사용자 요청으로 04장에 **Iceberg의 장점과 표준화 흐름**을 넣는다.
이 내용은 10-14에 도입부(01장)에서 뺐던 것인데, **04장이 제자리다** —
파일 구조를 다 본 직후라 “그래서 이 구조가 왜 좋은가”가 근거를 갖고 들어간다.

담을 것 (근거: [docs/md/lakehouse-concept.md](../docs/md/lakehouse-concept.md) 3·4절):

- **스냅샷으로 과거 조회·되돌리기** — 17쪽에서 본 스냅샷 4개가 근거
- **통계로 읽을 파일을 줄인다** — 19쪽에서 본 `order_id` 범위가 근거
- **엔진 독립** — 26쪽에서 흡수한 내용. *“SeaTunnel을 Spark로 바꾸면 Trino 설정을
  고쳐야 하나? → 아니다. 공유하는 건 HMS 주소와 `/lake` 경로 두 줄뿐”*.
  같은 파일을 Trino·PyIceberg로 읽은 것이 실제 근거다
- **표준화 흐름** — Databricks의 Tabular 인수, Snowflake Polaris, AWS S3 Tables,
  Delta Lake의 UniForm 호환. **“이미 1위”가 아니라 “수렴 중”**으로 말하고
  점유율 수치(39% vs 31%)를 같이 둔다
- 업계 동향은 **공개 자료 조사**이고 이번 실습에서 검증한 것이 아니라는 단서를 단다

앞 네 장에서 **실제로 본 것**이 그대로 장점의 근거가 되는 배치다.

### `구조는 데이터 크기와 무관하다` 슬라이드 삭제 (2026-10-21)

사용자: “실습한 5행이랑 전체 행이랑 비교하는 건 굳이 없어도 된다.”

- 이 장만 **5행 `retail.orders`가 주연**이었다. 덱 전체를 1억 행 기준으로 옮겨오는 동안
  (20쪽 샘플, 28쪽 검증표, 26쪽 설정 주석) 마지막까지 남아 있던 5행 잔재다.
- **뒤 장이 이 장의 수치를 쓰지 않는다.** “2천만 배 차이가 나도 깊이는 넷으로 같다”는
  흥미롭지만 근거로 재사용되는 곳이 없어, 빼도 끊기는 연결이 없다.
- **비교 대상이었던 20쪽은 남겼다.** 16쪽이 “파일 네 개를 차례로 따라가면 데이터가 나온다”고
  약속하고 17~20쪽 상단에 `①→②→③④` 진행 띠가 떠 있어, 20쪽을 빼면 ③에서 끊긴다.
  또한 26쪽 `조회 시 실제로 읽는 데이터량`의 `16.3 MB ↔ 15 KB`가 20쪽 표에서 나온 수치다.
- 삭제 후 남은 “5행” 문자열은 전부 **“2,500만 행 중 5행 샘플”** 용법이라 그대로 둔다.

### 12쪽 HMS 그림 검증과 크롭 (2026-10-19)

사용자가 “이 그림이 HMS를 제대로 설명하는 게 맞냐”고 물어 **실제 catalog-db에 질의해 대조**했다.

### 21쪽 카드에 미니 도식 추가 (2026-10-19)

### 11쪽 Iceberg 행 문구 교체 (2026-10-21)

`서버 아님 · docker ps에 없음 — 파일 포맷과 라이브러리`
→ `독립 실행 프로세스가 아님 — 데이터·메타데이터 파일(Parquet · Avro · JSON)과 그것을 읽고 쓰는 라이브러리로 존재`

사용자 요청: “`docker ps`에 없음” 같은 **관찰 방법**보다 **무엇으로 존재하는지**를 쓰자.
`docker ps` 표현은 재미있지만 (1) 도커를 안 쓰는 환경에서는 의미가 없고,
(2) “없다”만 말해서 **그래서 뭐냐**에 답하지 않는다. 바꾼 문구는 Parquet · Avro · JSON이라는
**04장에서 실제로 열어본 파일 이름**을 그대로 부르므로 뒤 장과 연결된다.
`docker ps` 한마디는 **발표자 노트로** 내려 말로만 덧붙인다.

### 13쪽 `카탈로그에 실제로 저장된 값` 추가 (2026-10-21)

사용자가 catalog-db를 직접 열어보고 “쿼리 결과도 12쪽에 같이 넣으면 어떨까”라고 제안했다.

- **스크린샷이 아니라 조판한 표로 넣었다.** 27쪽 Superset은 “실제 웹 UI”라는 사실 자체가
  메시지라 캡처가 맞지만, 여기서 보여줄 것은 **값**이다. DB 클라이언트 창을 캡처하면
  슬라이드 크기에서 글씨가 안 읽히고 툴 UI가 시선을 가져간다.
- **3 테이블 × 5열 요약 대신 테이블 하나의 `TABLE_PARAMS` 전체**를 보여준다.
  사용자가 처음 제안한 건 요약 쿼리 결과였지만, 한 테이블의 저장값을 통째로 보는 쪽이
  “카탈로그가 무엇을 아는가”를 더 정확히 전달한다. 등록된 세 테이블 이름은 하단 캡션에 적었다.
- 강조는 `metadata_location` 한 줄에만 준다(코드의 주황 하이라이트). 바로 아래
  `previous_metadata_location`이 `00003-…`으로 남아 **커밋 = 포인터 교체**가 눈으로 보인다.
- 오른쪽 카드 ②가 이 장의 핵심 — `numRows` · `snapshot-count`는 **HMS가 센 값이 아니라
  적재한 쪽이 계산해 넘긴 값**이다. 11쪽 “SQL 실행·Parquet 읽기 없음”과 모순되지 않는 이유다.
- **모든 값은 2026-10-20 세션에서 `docker exec … psql`로 직접 확인한 것**이다.
  `PARTITIONS` · `TAB_COL_STATS` · `HIVE_LOCKS`가 0행인 것도 같은 조사에서 나왔다.

- **대안으로 검토한 빨간 화살표 주석**: 코드 위에 절대좌표로 화살표를 얹어야 하는데
  이 덱은 `cqw` 기반이라 화면 폭이 바뀌면 화살표가 어긋난다. 표 방식을 택했다.
- **의도적으로 뺀 것**
  - `plugin_input`, `iceberg.table.upsert-mode-enabled` — 삭제한 OOM·transform 서사에
    딸린 값이라 발췌에서 제외했다. 발췌임을 발표자 노트에 적어 뒀다.
  - **`warehouse`는 기본 위치일 뿐**이라는 점(테이블 이름은 `production_orders_100m`인데
    디렉터리는 `..._append`, 실제 위치는 카탈로그에 기록된 값이 이긴다) — 슬라이드에서 빼고
    발표자 노트로 내렸다. 질문이 나오면 답하는 깊이로 판단했다.

### 04장 서술 교정 (2026-10-16) — 관찰을 규칙으로 쓰지 않기

사용자가 Codex와 실제 파일 구조를 검토해 **“이번 실행에서 관찰한 결과를 Iceberg의
보편 규칙처럼 쓰고 있다”** 는 문제를 제기했다. 17건을 고쳤다.
**고치기 전에 네 가지 사실 주장을 파일로 재검증했고 전부 맞았다.**

| 검증 항목 | 결과 |
|---|---|
| JSON 버전별 누적 스냅샷 (00000=0 … 00004=4개) | ✅ 일치 |
| “2만 배” → **2천만 배** (100,000,000 ÷ 5) | ✅ **내 계산 오류였다** |
| 네 Parquet 모두 2,500만 행 · row group 6개 | ✅ 일치 |
| 첫 row group 압축 후 16.3MB / 압축 전 57.4MB | ✅ 일치 (`…354905-a195136c…` 기준) |

**가장 중요한 교정 — Parquet과 manifest는 1:1이 아니다.**
이번 실행은 커밋마다 파일이 하나씩 늘어 1:1로 보였을 뿐이다.
manifest 하나가 Parquet 여러 개를 참조할 수 있으므로,
**“Parquet 10만 개 = manifest 10만 개”가 아니다.** 14·16쪽에 명시했다.

**그 외 주요 교정**

| 쪽 | 전 | 후 |
|---|---|---|
| 14 | “JSON은 맨 위 하나뿐” | “조회는 카탈로그가 가리키는 한 개에서 시작” + 과거 버전도 남는다 + format v2 기준 |
| 15 | “병렬도 4 → 커밋 4번” | “이번 실행은 네 번 커밋됐다. 병렬도와 커밋 수가 항상 같지는 않다” |
| 15 | “포인터만 바꾸면 그 시점으로 돌아간다” | “보존된 과거 스냅샷을 **지정해 조회**할 수 있다” — 과거 조회와 롤백을 구분 |
| 15 | “실제 파일 발췌” | “**주요 필드를 재구성한 예시**” — summary 중첩을 평탄화했으므로 |
| 16 | “COUNT(\*)가 빠른 이유” | “엔진이 메타데이터로 계산할 수 있다. **실제 적용 여부는 실행 계획으로 확인**” |
| 17 | “나머지 세 파일은 **열지도 않는다**” | “범위 통계상 **읽기 대상에서 제외할 수 있다**” — 실행 측정 근거가 없으므로 |
| 17 | “이 컬럼들로는 하나도 못 거른다” | “이 예시의 min/max로는 후보를 줄이기 어렵다” — 모든 조건으로 일반화하지 않음 |
| 18 | 5행 샘플로 전체를 입증한 듯한 서술 | “5행은 샘플. 전체 행 수는 footer, 전체 집계·범위는 별도 Trino 검증” |
| 19 | 2만 배 / “늘어난다” | **2천만 배** / “늘어날 수 있으며 파일 크기·쓰기 방식·병합 정책에 따라 다르다” |

**신설 22쪽 — 「엔진이 보장하는 것과 사람이 검증할 것」**

04장 아홉 장이 “엔진이 알아서 해준다”로만 읽히면 위험하다는 판단으로 추가했다.

> 원본 조회 조건을 잘못 써서 1억 행 중 9천만 행만 가져와도 Iceberg는 정상 커밋한다.
> **메타데이터가 정상인 것과 업무적으로 올바른 적재는 다르다.**

**커밋 단위 원자성과 작업(job) 단위 원자성의 구분**도 같이 담았다 —
여러 번 커밋하는 작업은 중간 실패 시 앞선 커밋이 이미 공개돼 있어,
전체를 `APPEND`로 재실행하면 중복된다. 우리 래퍼 스크립트가 그래서 재실행을 막는다.

**원칙** — 긴 조건·단서는 슬라이드 본문이 아니라 **발표자 노트**에 둔다.
본문에는 핵심만, 노트에는 “질문이 나오면 이렇게 답한다”를 적는다.

### 두괄식 전체 구성을 어디에 둘 것인가 (2026-10-15)

“전체 구성을 27쪽에 가서야 보여주는 건 순서가 거꾸로”라는 판단으로 **01장 끝에
전체 구성 슬라이드를 한 장 만들었다가, 같은 날 삭제했다.** 경위를 남긴다.

**만든 것:** 3열(쓰기 / 저장·카탈로그 / 읽기) 구성도를 HTML/CSS로 그리고 각 블록에
장 번호를 붙여 덱의 지도를 겸하게 했다.

**삭제한 이유 — 4쪽과 중복이고 더 나쁜 형태였다.**

4쪽(네 가지 역할) 아래에는 이미 **쓰기/읽기 흐름 띠**가 있다.

```
쓰기   원본 PostgreSQL → SeaTunnel → Iceberg 파일(./lake) + HMS 커밋
읽기   브라우저 → Superset → Trino → HMS에서 위치 확인 + ./lake 읽기
```

같은 정보를 **선형으로** 보여주는데, 새로 만든 5쪽은 이를 3열로 재배치하면서
아래 문제가 생겼다.

| 문제 | 내용 |
|---|---|
| 열 안에 연결선이 없다 | `원본 PostgreSQL`과 `SeaTunnel`이 쌓여만 있어 관계가 보이지 않는다 |
| 읽는 방향이 애매하다 | 오른쪽 열을 위에서 아래로 읽으면 `Trino → Superset → 브라우저`인데 요청 방향은 반대다 |
| 다이어그램이 아니라 표로 보인다 | 세 덩어리 나열이라 시스템 그림의 인상이 없다 |
| 주변 그림과 톤이 다르다 | `09`·`10`은 컨테이너 경계와 아이콘이 있는 그림인데 납작한 카드였다 |

**결론: 5쪽을 삭제하고, 쓸 만했던 「장 번호 길잡이」만 4쪽 띠로 옮겼다.**
4쪽 띠가 두괄식 역할을 겸하며, 한 장이 두 일을 한다 —
네 가지 역할을 보여주고, 아래 띠로 오늘의 순서를 예고한다.

**교훈:** 흐름은 **선형**일 때 가장 잘 읽힌다. 3열 배치는 요소가 많고 각 열 안에
순서가 있을 때 오히려 나빠진다. 또한 HTML로 그린 도형이 주변 PNG와 섞이면
완성도 차이가 드러난다 — **단순한 띠 수준이면 HTML이 낫고, 컨테이너 경계와
아이콘이 필요한 그림이면 PNG가 낫다.**

진짜 전체 구성도가 필요해지면 `09`·`10`과 같은 스타일의 PNG를 만드는 편이 낫다.

**→ 실제로 그렇게 했다 (2026-10-15).** 사용자가 codex로 `11-local-lakehouse-overview`를
생성했고, v3에서 아래 세 가지를 반영해 **6쪽에 넣었다.**

| 수정 | 이유 |
|---|---|
| “컨테이너 서비스 · 웹 브라우저” → **“Docker 컨테이너”** + 고래 아이콘 | `09`와 톤을 맞춘다 |
| **웹 브라우저를 Docker 박스 밖으로** | 브라우저는 호스트에서 실행되며 컨테이너가 아니다. 03장이 역할 경계를 따지는 장이라 여기서 어긋나면 앞뒤가 안 맞는다 |
| **상단 큰 제목 제거** | `09`·`10`처럼 잘라내는 수고를 없앤다 |

**범례의 주황(적재)/파랑(조회)이 그대로 덱의 지도 역할을 한다** — 02장은 주황,
05장은 파랑. 그림 자체의 색 구분이 목차와 일치하는 구조라 캡션 한 줄로 예고가 된다.

### 제목 작성 규칙 (2026-10-16 확정)

사용자 지적: **“제목들이 전반적으로 AI스럽다.”** 원인을 찾아 규칙으로 고정한다.

**원인 — 제목이 명사구가 아니라 문장이었다.** 네 가지 유형이 섞여 있었다.

| 유형 | 고치기 전 예시 |
|---|---|
| 완전한 서술문 주장 | “파일을 쓰는 것과 테이블이 되는 것은 다른 단계다” · “구조는 데이터 크기와 무관하다” |
| 수사적 의문문 | “왜 Iceberg가 표준처럼 쓰이나” · “왜 이 조합을 골랐나” |
| 과장·극적 표현 | “카탈로그가 하는 일은 **생각보다 작다**” · “실제로 읽는 건 **일부다**” |
| 문장—문장 대시 | “조회 계층을 붙인다 — 설정으로 연결하고, Trino가 읽는다” |

**규칙**

1. **제목은 명사구로 쓴다.** 그 슬라이드가 *무엇인지* 지칭하면 충분하다.
   `Hive Metastore의 역할`, `적재 작업 설정`, `구성요소 선택 근거` 처럼.
2. **주장·설명·수치는 부제(`s-sub`)로 내린다.** 제목에서 뺀 문장을 버리지 않는다 —
   예: 제목 `적재 흐름` / 부제 “파일을 쓰는 것과 테이블이 되는 것은 다른 단계다.”
3. **수사적 의문문을 쓰지 않는다.** “왜 ~인가” → “~의 근거”, “~와 ~”.
4. **대시(—)는 명사구끼리 연결할 때만.** `③ manifest — Parquet 경로와 통계`는 괜찮고,
   `조회 계층을 붙인다 — 설정으로 연결하고…`처럼 문장을 잇는 용도로는 쓰지 않는다.
5. **제목에 강조 색을 넣지 않는다.** 단, **색이 내용과 1:1로 대응할 때만** 예외 —
   10쪽 `각자 하는 일과 하지 않는 일`은 표의 두 열 색(파랑/주황)과 짝이 맞아 유지했다.

깨지기 쉬워서다. 수정 라운드가 많을 것으로 예상되는 점도 고려했다 — 내용 수정은
텍스트 파일 쪽이 훨씬 빠르고 안전하다.

PDF가 필요하면 브라우저 인쇄(가로 방향)로 뽑는다. 인쇄 스타일을 넣어두었고

## 7. 외부 자료 검증 기록 (16~22쪽의 근거)

2026-10-12, 국내 블로그 글 <https://spidyweb.tistory.com/603> 의 Iceberg 메타데이터 설명을
**우리 저장소의 실제 파일과 대조**했다. 16쪽의 “흔한 오해 셋”과 17~20쪽에 실린 실제 값이
모두 여기서 나왔다.
`docs/md/iceberg-json-to-parquet.md`의 “제공된 Gemini 설명 검토” 표와 같은 방식이다.

### 검증 방법

```sh
# ① metadata JSON 구조 — 최상위 키와 데이터 파일 경로 포함 여부
python3 -c "import json; d=json.load(open('lake/.../orders/metadata/00002-….metadata.json')); print(d.keys())"

# ② 파일 머리 4바이트로 실제 포맷 확인
head -c 4 lake/.../metadata/snap-….avro | xxd -p     # → 4f626a01

# ③ Avro 내용 — 프로젝트 venv의 fastavro 사용
.venv/bin/python -c "import fastavro; print(list(fastavro.reader(open('….avro','rb'))))"
```

### 결과

| 글의 주장 | 실제 확인 | 판정 |
|---|---|---|
| manifest list는 **JSON** | `snap-…​.avro`, 매직바이트 `4f626a01` = `Obj\x01` | **틀림 — Avro** |
| manifest file은 “상세 정보를 담은 **JSON 파일**” | `…-m0.avro`, 같은 매직바이트 | **틀림 — Avro** |
| **Snapshot Files (JSON)** 가 별도 계층으로 존재 | 그런 파일 없음. 스냅샷은 metadata JSON 안의 `snapshots` 배열 | **틀림 — 계층이 하나 많다** |
| Table Metadata가 “**데이터 파일 목록**” 포함 | 최상위 키 21개 중 없음. `.parquet` 문자열은 `write.parquet.compression-codec` 속성에만 등장 | **틀림 — 포인터만 있다** |
| 스냅샷당 manifest list **여러 개** | 스냅샷 1개 ↔ `manifest-list` 1개 (단수 필드) | **틀림 — 1:1** |
| 디렉터리 예시 `snap-xxxx.json` · `manifest-xxxx.json` | 전부 `.avro` | **틀림** |
| 파일 크기 “**1GB 내외** 권장” | Iceberg 기본값 `write.target-file-size-bytes` = **536870912 (512MB)** | **근거 없음** |
| 계층을 따라가는 전체 방향 | 맞다 | 맞음 |
| metadata 파일은 immutable, 변경 시 새 파일 | 맞다 (`metadata-log`에 과거 JSON 4개 보존 확인) | 맞음 |
| manifest 통계로 파일을 걸러낸다 | 맞다 (`lower_bounds`/`upper_bounds` 실측 확인) | 맞음 |
| compaction · snapshot expiration · orphan file deletion | 맞다 | 맞음 |

**`snap-`으로 시작하는 파일이 manifest list인데 이름 때문에 “스냅샷 파일”로 오해한 것**으로 보인다.
이 오해가 계층을 4단에서 5단으로 늘렸다.

### 실측한 값 (슬라이드에 쓴 숫자의 출처)

```text
retail.orders (5행)
  metadata JSON 최상위 키 21개 · snapshots 2개 · current-snapshot-id 7763263029727631105
  manifest list(snap-….avro) 레코드 2개 → manifest 2개
  manifest(…-m0.avro) 레코드 1개 → data_file 1개
    file_format=PARQUET · record_count=2 · file_size_in_bytes=1196
    lower_bounds customer=Dave status=DONE order_id=1004
    upper_bounds customer=Eve  status=NEW  order_id=1005

production_orders_100m (1억 행) — 커밋 4회 누적
  seq1 +25,000,000 → total 25,000,000 (files 1)
  seq2 +25,000,000 → total 50,000,000 (files 2)
  seq3 +25,000,000 → total 75,000,000 (files 3)
  seq4 +25,000,000 → total 100,000,000 (files 4)
  metadata-log 4개 (과거 metadata JSON 이력)
```

### 발표에서 다룰 때 주의

- 블로그 **출처를 슬라이드에 적지 않는다.** 특정 글을 공개적으로 지적하는 모양이 되면
  발표의 초점이 흐려진다. “자료를 찾다 보면 자주 보이는 설명”으로 일반화해 적었다.
- 교정의 근거는 **우리 파일**이다. 남의 글이 틀렸다는 게 요점이 아니라,
  **직접 열어봐서 안다**는 게 요점이다.
- 19쪽 하단 단서(“조건에 맞는 파일만 정확히 읽는 것은 아니다”)는 반대 방향의 과장을
  막는 장치다. 메타데이터 구조가 속도를 보장하지는 않는다.

## 8. 예상 질문과 답

발표 후 나올 법한 질문을 미리 정리했다. 모르는 건 모른다고 말한다.

| 질문 | 답 |
|---|---|
| 왜 Hive Metastore인가? REST Catalog도 있지 않나 | **9쪽에서 이미 다룬다.** HMS가 Iceberg의 유일한 선택지가 아니다. SeaTunnel과 Trino 양쪽이 바로 지원해 추가 구현이 없다는 점 때문에 골랐다. JDBC·REST 카탈로그도 가능하다 |
| 운영에 쓸 수 있나 | 아니다. 단일 Mac, 로컬 파일시스템, 단일 노드 Trino다. 운영은 객체 저장소(S3 호환)와 다중 노드가 전제다. 전환 설계는 `docs/local-lakehouse-build-options.md`에 있고 **검증은 안 했다** |
| 정말 조회 엔진을 갈아끼울 수 있나 | 같은 파일을 Trino와 PyIceberg 노트북으로 읽어봤다 (27쪽). 다만 **카탈로그 교체는 안 해봤다** — 31쪽에 다음 과제로 적어뒀다 |
| 1억 행이 왜 Parquet 4개인가 | 병렬도 4로 읽어 writer가 4개였고 각각 2,500만 행을 썼다. 목표 파일 크기 128MiB를 설정했지만 zstd 압축 후 파일당 약 82MB라 분할되지 않았다 |
| 재적재하면 어떻게 되나 | `APPEND_DATA`라 중복된다. 그래서 래퍼 스크립트가 테이블·경로·실행 기록을 검사해 재실행을 막는다 (15쪽) |
| Superset에서 1억 행을 다 보나 | 아니다. 집계와 `LIMIT` 샘플만 본다. 전체 전송은 브라우저가 못 버틴다 |
| 1억 행 적재할 때 문제는 없었나 (슬라이드에 없음) | 있었다. 원본 PK 정보가 sink까지 자동 전달되면서 키별 위치를 들고 있는 writer가 선택돼 메모리가 찼다. 중간 변환에서 그 정보만 떼어내 해결했다. **발표 범위 밖이라 뺐고**, 상세는 `docs/production-orders-100m.md`와 `evidence/production-100m/attempt1·2/diagnosis.md`에 있다 |

## 9. 발표 진행 메모

- **3·4쪽은 개념 도입**이다. 팀원 중 레이크하우스가 처음인 사람 기준으로, 깊이 들어가지 않는다.
  Iceberg 표준화나 벤더 비교를 물으면 `docs/md/lakehouse-concept.md` 기준으로 말로 답한다.
- **4쪽(네 가지 역할)이 이 발표의 뼈대다.** 02~05장이 전부 이 네 칸의 전개이므로,
  여기서 네 칸을 확실히 심어두면 나머지가 쉽게 따라온다.
- **7·9·11쪽과 16~22쪽(walkthrough)에 시간을 가장 많이 쓴다.** 전체 23분 중 13~14분.
  이 두 묶음이 과제의 두 축(환경 세팅 · Iceberg 동작 원리)이다.
  “환경을 이해했는가”에 답하는 구간이 여기다.
- 6·8·13·24·29쪽은 **그림이 주인공**이다. 읽지 말고 손으로 짚으며 흐름만 설명한다.
- 11쪽(함정 셋)은 **해결책까지만** 말한다. 셋 다 같은 성격이라는 마무리가 요점이고,
  각 사건의 전말을 풀면 발표의 초점이 흐려진다.
- **적재 중 겪은 메모리 문제는 먼저 꺼내지 않는다.** 질문이 오면 한두 문장으로
  답하고 `docs/production-orders-100m.md`로 안내한다 (8절 참고).
- 25쪽 `local.location=/` 는 질문이 나오기 쉬운 지점이다.
  `/lake`로 쓰면 `/lake/lake/...`가 된다는 주석을 그대로 읽어주면 바로 이해된다.
- 30쪽 첫 줄은 4쪽에서 한 말과 **똑같이 반복**한다. 의도된 반복이다.

## 10. 이 기획에서 의도적으로 뺀 것

- **SeaTunnel 자체 개념** — 선행 발표에서 다뤘다. 중복이다.
- **적재 도구의 메모리 문제 전체** — 3절에 적은 이유로 **슬라이드에서 완전히 뺐다.**
  기록은 `docs/production-orders-100m.md`와 `evidence/production-100m/`에 보존돼 있다.
- **적재 성능 수치** — 159초는 3쪽에서 “됐다”의 근거로 한 번만 쓰고 따로 다루지 않는다.
- **CDC·스트리밍** — 이번 구축은 정적 배치 적재만 했다. 안 해본 걸 말하지 않는다.
- **S3 전환 / MinIO** — 설계만 있고 실행 검증이 없다. 31쪽에 한 줄로만 둔다.
- **Iceberg 스펙 상세**(삭제 파일, 파티션 진화, 스키마 진화) — 이번 실습이 추가(append)
  전용이라 경험한 범위를 벗어난다. 질문 나오면 “안 다뤄봤다”고 답한다.
- **벤치마크** — 159초와 5.872초는 **단일 실행 기록**이지 성능 측정이 아니다.
