같은 “메타데이터”지만, 저장하는 범위가 다릅니다.

CATALOG-DB / TABLE_PARAMS

현재 테이블을 찾기 위한 등록정보

table_type = ICEBERG
metadata_location = file:/lake/.../00002-….metadata.json
previous_metadata_location = file:/lake/.../00001-….metadata.json
current-snapshot-id = 7763263029727631105
numRows = 5

핵심은 metadata_location입니다. 스키마나 현재 스냅샷 요약도 편의상 함께 저장될 수 있어 일부 정보는 겹칩니다.

이 예시는 evidence/02-hms.txt의 실제 기록을 축약했습니다. 파일명에 들어간 …는 화면 표시용 생략입니다.

HMS가 lake/를 주기적으로 훑어서 JSON·Avro 내용을 전부 DB에 복사하는 구조가 아닙니다. Iceberg writer가 커밋 과정에서 새 메타데이터 위치와 필요한 속성을 등록·갱신합니다.

HMS 서버 자체를 직접 개발할 필요는 없습니다. 현재는 공식 Hive 이미지가 서버를 실행하며, 우리는 연결 주소·드라이버·영구 저장소를 설정합니다. prepare_catalog.py는 HMS API를 통해 retail namespace만 준비합니다.

처음 구축할 때 자주 헷갈리는 것

Trino가 catalog-db에 직접 붙으면 안 되나요?

PostgreSQL 커넥터로 HMS 내부 테이블을 조회하는 것은 가능합니다. 하지만 그것은 Iceberg 주문 테이블 조회와 다른 작업입니다. 현재 Iceberg Hive catalog 구현은 HMS API를 통해 테이블을 찾습니다. 내부 DB 구조 대신 서버 API를 사용하고, 여러 클라이언트가 같은 등록·갱신 규칙을 따르게 합니다.

Iceberg에는 HMS가 무조건 필요한가요?

현재 선택한 Hive catalog 구성에는 HMS가 필요합니다. Iceberg 전체의 필수 구성요소는 아닙니다. REST catalog 등 다른 카탈로그 구현을 선택할 수도 있습니다. 지금 실습은 Hive catalog이므로 HMS를 통해 접근합니다.

hms.txt 파일도 HMS가 사용하는 저장소인가요?

아니요. evidence/02-hms.txt는 scripts/catalog.sql로 catalog-db를 SELECT한 결과를 사람이 확인하도록 저장한 기록입니다. 실제 서비스는 이 텍스트 파일을 읽지 않습니다. 과거 기록이므로 이후 커밋이 생겨도 자동으로 바뀌지 않습니다.

다음 데이터가 들어오면 무엇이 바뀌나요?

writer가 새 파일과 새 metadata JSON을 작성하고, 성공적인 커밋으로 현재 JSON 포인터를 교체합니다. 과거 JSON을 매번 덮어쓰는 방식이 아닙니다. catalog-db의 현재 위치·관련 속성은 갱신됩니다. 데이터가 없는 속성 변경 커밋은 새 스냅샷을 만들지 않을 수도 있습니다.

서비스를 켰는데 조회가 안 되면 어디부터 볼까요?

① HMS가 기동됐는지 → ② HMS의 PostgreSQL 연결과 JDBC 드라이버가 맞는지 → ③ retail.orders가 등록됐는지 → ④ metadata_location의 /lake 경로를 Trino가 실제 읽을 수 있는지 확인합니다. 등록정보가 존재해도 파일 마운트나 권한이 잘못되면 조회는 실패합니다.
