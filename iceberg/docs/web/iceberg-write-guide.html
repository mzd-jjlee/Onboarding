01 / 쓰기 과정

데이터에서 메타데이터로, 다섯 단계

새 행을 추가하는 append 적재를 단순화한 예시입니다. 아래 파일명과 2행 데이터는 설명용이며 실제 파일 출력이 아닙니다.

논리적인 설명 순서입니다. 실제 writer는 병렬로 동작할 수 있고, 한 job에서 여러 스냅샷이 커밋될 수 있습니다. 빈 테이블 생성 시 데이터 없는 초기 JSON이 먼저 생길 수도 있습니다.

실제 파일 탐색 / RETAIL.ORDERS

배치가 두 번 쌓이면, JSON 하나로 5행을 찾을까요?

네. 현재 JSON을 시작점으로 선택한 스냅샷의 manifest list를 따라가면, 기존 배치와 추가 배치의 파일을 함께 찾습니다. 과거 JSON을 하나씩 열어서 행을 합치는 방식이 아닙니다.

기준은 HMS에 커밋된 metadata_location입니다. 폴더의 수정 시간이나 가장 큰 파일명으로 최신 JSON을 고르지 않습니다. 기존 JSON을 덮어쓰기보다 새 버전을 작성하고 현재 포인터를 바꿉니다.

아래는 로컬 orders 테이블의 실제 JSON·Avro·Parquet을 읽어 HTML에 내장한 기록입니다. 현재 포인터는 evidence/02-hms.txt에 저장된 당시 값이며 실시간 DB 조회가 아닙니다. ‘커밋 전’은 그 기록을 이용한 설명용 시나리오입니다. 큰 ID는 브라우저의 숫자 반올림을 피하려고 문자열로 표시하며, Avro bytes는 bytes_hex로 표시합니다.

주기적 배치에서 더 알아둘 점

커밋 주기와 writer 동작에 따라 한 배치에 여러 스냅샷이 생길 수 있습니다. 배치 1회 = JSON 1개 = Parquet 1개라는 규칙은 없습니다. 이 실습에서 첫 배치와 두 번째 배치는 각각 파일 1개를 추가했습니다.

같은 원본 범위를 APPEND로 반복 적재하면 중복될 수 있으므로 배치별 추출 범위·처리 위치를 관리해야 합니다. 파일이 계속 늘어나면 작은 파일 병합·스냅샷 만료 같은 유지관리도 고려합니다. JSON·Avro를 직접 삭제해서 정리하지 않습니다.

02 / 조회 과정

Trino는 참조를 따라 파일을 찾습니다

HMS에서 현재 JSON 위치를 받은 다음, 선택한 스냅샷이 가리키는 파일을 읽습니다. 폴더에 있는 Parquet을 무조건 전부 합치는 방식이 아닙니다.

HMS
현재 JSON 위치→JSON
스냅샷 선택→Manifest List
Avro→Manifest
Avro→데이터
Parquet

Superset은 SQL 요청과 결과 화면을 담당합니다. 파일 읽기와 SQL 계산은 Trino가 수행하며 캐시·통계 기반 파일 제외로 실제 읽기 작업은 달라질 수 있습니다.

큰 테이블과 컬럼 선택

JSON 하나가 1억 행을 담는 건 아닙니다

예를 들어 현재 스냅샷에 Parquet 4개가 각각 2,500만 행을 담고 있다면, 최신 커밋 포인터가 가리키는 metadata JSON 하나가 그 스냅샷을 고르고, manifest list와 manifest들이 4개 파일 경로를 나누어 가리킵니다. 엔진은 그 경로를 따라 필요한 파일을 읽어 합쳐 1억 행의 테이블처럼 SQL 결과를 만듭니다.

현재 metadata
snapshot S→Manifest list
Manifest A · B→Manifest A
Parquet 1 · 2+Manifest B
Parquet 3 · 4

4개 파일·manifest 2개는 설명을 위한 가상 배치입니다. 파일이 매우 많아지면 여러 manifest에 나뉩니다. 현재 JSON은 시작점 하나지만, JSON 하나 안에 모든 경로나 행이 직접 들어 있는 것은 아닙니다. 선택한 스냅샷의 파일 집합은 그 manifest들의 유효한 항목으로 정해집니다.

컬럼 하나를 선택하면

SELECT quantity
FROM iceberg.retail.production_orders_100m;

Trino는 먼저 같은 메타데이터 경로로 스냅샷과 대상 파일을 찾습니다. 그다음 Parquet은 컬럼형 포맷이므로, 이 쿼리 결과에 필요한 quantity 컬럼의 데이터 영역만 요청할 수 있습니다. WHERE status = ... 조건이 있으면 status도 필요합니다. 컬럼 일부만 읽는 것과 파일 일부만 읽는 것은 다른 최적화입니다.

파일을 건너뛸 수는 있지만 항상 건너뛰는 것은 아닙니다. manifest·파일 통계, 파티션, 조건식에 따라 후보를 줄일 수 있고, 조건이 모든 행에 걸리거나 통계로 판단할 수 없으면 여러 파일을 확인해야 합니다. 컬럼 선택은 읽을 컬럼 바이트를 줄여도, 후보 파일의 메타데이터를 계획하는 일까지 없애지는 않습니다.

이 프로젝트의 1억 행 테이블은 상태별 2,500만 행으로 구성되고 Parquet 4개가 등록됐습니다. 다만 현재 테이블은 비파티션 테이블이라 상태 조건만으로 파티션을 통째로 제외하지는 못합니다. 파일 통계 기반 제외 여부는 각 파일의 기록된 범위에 달려 있습니다.

03 / 추가 적재

기존 데이터를 매번 복사하지 않습니다

상태스냅샷이 포함하는 데이터 파일의미
스냅샷 Apart-a.parquet첫 적재 결과
스냅샷 Bpart-a.parquet + part-b.parquet기존 파일과 추가 파일을 함께 참조

새 스냅샷은 기존 manifest를 재사용하거나 필요에 따라 합칠 수 있습니다. Parquet 하나당 JSON·Avro가 반드시 하나씩 생기는 관계는 아닙니다.

파일 생성과 커밋 성공은 별개입니다. 새 파일이 있어도 커밋되지 않았다면 현재 테이블 상태에 포함되지 않을 수 있습니다. 파일 저장과 PostgreSQL 반영을 하나의 DB 트랜잭션으로 묶는 것은 아닙니다.

헷갈리기 쉬운 질문

Avro에도 원본 주문 데이터가 한 번 더 저장되나요?

이 구조의 manifest Avro에는 데이터 파일 경로·행 수·통계 등이 들어갑니다. 원본 주문 행 전체를 중복 저장하는 용도가 아닙니다. manifest list도 별도의 Avro이며 manifest들의 목록과 요약 정보를 담습니다.

HMS가 lake/를 스캔해서 파일을 등록하나요?

아닙니다. Iceberg 라이브러리가 작성한 테이블 상태를 HiveCatalog를 통해 HMS에 등록·갱신 요청합니다. HMS는 파일 작성기가 아닙니다.

catalog-db에는 JSON 경로만 있나요?

테이블 이름·위치·속성 등이 있고, 스키마·스냅샷 정보 일부도 중복 저장될 수 있습니다. 다만 JSON·Avro·Parquet 파일 전체를 catalog-db에 넣는 것은 아닙니다.

조회 중에 새 데이터가 커밋되면 섞이지 않나요?

조회는 선택한 스냅샷을 기준으로 읽습니다. 새 상태가 커밋돼도 기존 조회가 작성 중인 파일을 섞어 읽는 방식은 아닙니다. 이후 조회에서 새 상태를 확인할 수 있습니다.
