초록 계열 상자는 Airflow 컨테이너 안에서 도는 Python(src/public_api/weather.py)이고, 파란 상자만 실제로 Iceberg에 쓴다.

ETL인가, ELT인가

지금 구조는 ETL이다. 변환(T)이 적재(L)보다 먼저 일어난다. Open-Meteo는 {time:[…], temperature_2m:[…]}처럼 열마다 배열을 따로 주는데, collect가 이걸 한 시간 = 한 행으로 바꾸고 +09:00을 붙이고 null·단위를 검사한 뒤에야 CSV로 내려놓는다. Iceberg에는 검증을 통과한 행만 들어간다.

ELT로 하려면 원본 JSON을 먼저 Iceberg raw 테이블에 넣고 Trino SQL로 펼쳐서 정제 테이블을 만들어야 한다. 이 프로젝트의 Trino는 읽기 전용(READ_ONLY)이라 지금은 그 경로가 막혀 있다. 원본 JSON은 대신 evidence 폴더에 실행마다 보관한다.

며칠치씩 이어 받는 방식

범위는 Airflow의 실행 날짜가 아니라 테이블에 실제로 들어 있는 마지막 날짜로 정한다. 그래서 실행끼리 겹치지 않고, 실패한 날짜는 다음 실행이 다시 받는다.

한 칸 = 하루, 2025-10-01~10-24. 마지막 줄은 아직 실행 전의 계산값이다.

이 작업, SeaTunnel만으로 할 수 있나

SeaTunnel 2.3.13 이미지에는 HTTP source(connector-http-base)가 들어 있어서, 이론상 CSV 없이 API를 바로 읽을 수 있다. 문서만 보고 판단하지 않으려고 API → SQL 변환 → Console 출력 job을 실제로 돌려 봤다(Iceberg에는 쓰지 않음).

실패응답을 행으로 펼치기. 오류: Paths have different array parents

HTTP source의 json_field는 $.data[*].temp처럼 같은 배열 안의 객체에서만 행을 만든다. Open-Meteo는 열마다 배열이 따로 있어서($.hourly.time[*], $.hourly.temperature_2m[*]) 하나의 행으로 묶지 못한다. SQL transform은 한 행을 여러 행으로 펼치는 기능이 없어 이 단계를 대신할 수 없다.

json_field = {
  weather_time   = "$.hourly.time[*]"
  temperature_2m = "$.hourly.temperature_2m[*]"   ← 여기서 실패
}

판단

지금 구조가 맞다

Airflow는 언제·어디부터·괜찮은지를 판단하고, SeaTunnel은 데이터를 옮긴다. 각 도구가 잘하는 일만 맡는 구조다. SeaTunnel만으로는 스케줄과 이어 받기 범위 계산을 할 수 없어서, 결국 바깥에 무언가가 필요하다.

CSV는 필수인가

이 API에서는 사실상 그렇다. 열 배열을 행으로 바꾸는 중간 단계가 필요하고, 그 결과를 SeaTunnel이 읽을 수 있는 파일(CSV나 JSON Lines)로 내려놓는 게 가장 단순하다. 응답이 [{…}, {…}] 형태인 API라면 SeaTunnel HTTP source가 바로 읽을 수 있다(이 경우는 문서 기준, 미실행).
